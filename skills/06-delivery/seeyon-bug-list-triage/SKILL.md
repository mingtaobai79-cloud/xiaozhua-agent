# 客户 Bug/需求清单分诊

## When to Use

- 客户（或项目经理）给一张 bug/需求表，问「哪几个简单」「先做哪个」「这个要多久」。
- 要按处理人/状态捞一批条目，然后排期、派活或评估改动面。
- 要把业务描述对到具体的 UDC 页面 / 微流程 / 子页面资源上。

不用于：单条 bug 的根因定位（那是 `seeyon-runtime-incident-response`）；环境连接（那是 `seeyon-low-code-environment`）。

## 输出要求（用户偏好，先记住）

- **先给具体清单**：哪几条先改、哪几条可以留，一条一条列出来；分级框架只用一句话带过。
  用 A/B/C/D 分类体系开场会被读成「没回答我的问题」——用户要的是条目，不是分类学。
- 顺序固定：**口径确认 → 清单 → 分级 → 排序建议**。
- 排序建议直接给「先做 A → B → C」并说理由，**不要给选择题**、不要把全部可能性列出来让用户挑。
- 用户常带一个**留白额度**（如「我可以留三个不改」）：主动给出「先改 N 条 + 可留 N 条」两组，
  并说清这几条为什么可以留（多为新功能开发 / 依赖老系统数据迁移 / 需求本身待澄清）。
- 用户说顺序和他不一样时，**不要重申自己的理由**：直接把「你留哪几条」问出来，再按他的口径重排一遍。
- 每条注明证据等级：STATIC（类名/产物索引）/ LIVE（环境实测）/ UNVERIFIED；拿不准的写「需要进一步核对」。
- 「对应哪个页面/微流程/子页面」是分诊的核心价值，但**不要用它替代 bug 原文**：用户要把结论贴回表里、
  转给别人时会要求「描述写清楚」——原文逐字还原见第 5 节。
- 清单全文和索引存到任务目录（如 `<PATH><客户>/<任务名>/`），**按任务新开目录，不覆盖历史证据目录**——同一张表不同时间的数据本身就是证据。

## 1. 先定口径，再数数

- **先看输入里已有的锚点。** 用户丢一张筛选界面截图时，图里已有信息就是锚点：可选的状态集合、模块筛选、
  以及截图上露出的其他窗口/列表文字（含编号和报错文案）。**先把整张图的文字读全**（字小/被裁切时按
  `region` 裁区域放大再读，不要只读一眼就下结论），再拿图里出现的编号/文案去表里搜到对应记录。
- **报错文案用「原文」，不要用用户口语转述。** 用户描述「提示不是100%」，表里/界面上的真实文案往往是
  「付款信息中的付款比例必须等于100%」。**两者对应到完全不同的代码位置**：用真实文案去搜才能命中校验节点。
- **条目清单是会变的，缓存数据不能当今天用。** 飞书表快照一落盘就带上了时间；用户隔一段时间再提同一张表，
  必须重新取数再回答。两次快照条数不一样不是矛盾，是表真变了——旧快照只能当历史证据，不能拿来答「现在有哪几条」。
  手头只有旧快照又要先给结论时，**明确标出快照日期与当时条数**，并说清为什么对不上。
- 状态词以**表里的选项**为准，不要用用户口述的词：用户说「为解决」，表里实际选项可能是「未解决」。
  先打印状态分布核对口径，回答里写明「你说的 X = 表里的 Y」。
- 「我的」清单可能来自 `处理人` / `提交人` / `修改人` 三种口径，各数一遍，取与用户说的条数吻合的那个。
  只筛「处理人=某人」常常多出一条（不属于用户说的模块/范围）——同时按模块字段再筛一道，能对上才是口径对了。
- 分类字段（业务逻辑 / 功能缺失 / …）通常只有少数几条有值，不能拿它做主筛选维度。
- 用户说「应该还有 N 条」时，先把自己数出的条数和口径一起报出来，再往下分析；数字对不上要直接说。

## 2. 取数前置：两个必查项

飞书多维表格走 CDP 取数的完整步骤见 `feishu-bitable-cdp-extract` skill；下面两条是那套流程里最容易翻车的地方，每次先确认：

1. **记录的值表不一定有 `fields` 包层**，两种形状都存在：`recordMap[rid].fields[fid]` 或 `recordMap[rid][fid]`。
   统一写 `f = recs[rid].get("fields") or recs[rid]`。只认 `.fields` 会把整表读成全空/全 None，然后误判成「表里没数据」；
   统计出全 0 / 全 None 时，先怀疑容器形状，不要下结论。
2. **9222 未监听时先自己起，不要停下来问用户**：用 Debug profile 起后台进程（勿动用户主 profile），
   `--remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir=<Debug User Data>`，
   起来后 `curl -s http://127.0.0.1:9222/json/version` 验证。profile 切换细节见 `chrome-profiles` skill。
   但如果**已存在的调试实例是隔离 profile（打开表直接跳登录页）**，那一步就不是“没监听”而是“没登录”：
   直接请用户在那个调试窗口里登一次（他会同意），登录后同一 tab 读到非空 `document.cookie` 就继续抓。
   两种情况下都不要去拷用户主 profile 的 cookie 库。

解 gzip+base64 载荷后要打印中文时：脚本里 `sys.stdout.reconfigure(encoding='utf-8')`，命令前加 `PYTHONIOENCODING=utf-8`，
用 `uv run --no-project python x.py` 跑（不依赖全局 pip/虚拟环境）。

## 3. 分级：按改动面从小到大

| 级别 | 特征 | 为什么便宜 / 贵 |
|---|---|---|
| 低代码资源内改动 | 页面 / 子页面 / 微流程 / 配置表字段的取值、展示、生成结果 | 改动面窄、逐项可验，验收就是「生成或显示对不对」 |
| 需元数据或表结构变更 | 字段拆分、新增配置项、新增选项 | 要改元数据并**回读元数据**验收，还牵动已有数据 |
| 跨系统数据迁移 | 从老系统拉模板 / 配置 / 附件 | 要连老环境取数 + 对账，工作量不可控 |
| 新功能开发 | 新按钮 / 新弹窗 / 新权限矩阵 / 新配置功能 | 需求本身还要澄清，不属于「修 bug」 |

判定看描述里的动词：**「显示/取值不对」「没生成」** → 前两级；**「要能配置」「要新增」** → 第四级；
**「从老系统迁过来」** → 第三级。附件权限矩阵、审批人取值规则这类「多分支但都落在已有资源里」的条目算中等，
不要因为分支多就归到新开发。

## 4. 把 bug 描述对到具体资源（不要凭经验猜）

- 本地反编译产物（customer-web 等）里微流程控制器类名是**拼音**，可直接反推业务含义：
  `MicroFlow` + 拼音 + `Controller`，如 `Ht`=合同、`Sqd`=申请单、`Sp`=审批、`Gl`=管理、`Xq`=详情、
  `Ly`=列表页、`Ziyemian`=子页面、`Khlshzqk`=考核利润情况。
- 用按版本建的类名清单（如 `microflow-index.json`）把 bug 的功能点对上**具体微流程 / 子页面**，再据此判改动面；
  对不上就是「资源不存在 → 属于新开发」的信号。
- 类名索引来自**某个版本**的反编译产物，是 STATIC 证据，必须带版本号；javap 输出的中文在采集阶段可能已损坏成
  `U+FFFD`（不可恢复），**只有 ASCII 类名可靠**，别拿乱码 caption 当结论。
- 要落到资源 ID 和运行态清单，必须再去环境（UAT/test2）核对，不能把静态索引说成运行态事实。

## 5. 逐条交付：原文 + 实现方式

用户说「把 bug 描述写清楚」或「写上对应的实现方式」时，交付物从分诊清单切换成逐条明细，每条固定四段：

```
[序号] 记录ID  状态 / 分类 / 优先级
描述：
（源表描述原文，逐字放进 fenced block）
实现方式（改动落点：页面 / 子页面 / 微流程 / 配置表）：
1. …
2. …
```

- **原文逐字还原**：错别字、中英混排、重复编号、口语都照抄——这些痕迹是定位线索，改了就丢信息。
  摘要式压缩（「字段重复、多余特殊字段」）会被直接要求重写。
- 实现方式 = **改动落点 + 改法建议**，编号即执行顺序；条目间用分隔线隔开，便于用户逐条复制。
- 结尾必须声明：实现方式是依据描述 + 已有资源给出的**建议**，落到具体字段/微流程 ID 需在设计器里核对。
- 同时落成本地 markdown 文件（任务目录下）并在回答里给绝对路径。

### 逐条查证时：先看图，再定根因，最后给方案

- **bug 附件里的截图是现象的第一手证据，优先下载来看。** 附件 token 在记录字段值里（不在 `resourceMap`），
  取法与批量下载见 `feishu-bitable-cdp-extract` skill。截图能直接区分「这是表单页问题还是生成文档问题」——
  跳过这步会把页面布局类问题误归到模板/后端。
- **每条固定给「现象（截图实拍）→ 根因（产物/DB 证据）→ 方案 → 要用户拍板的那一个点」。** 建议按投入产出排
  先后（把同一根因的几条并成一批修），并说清哪条只是相关、哪条是同一个根因。
- **对不具备的输入要直接说缺什么，不要瞎猜。** 模板是 `.doc` 原件、老系统数据这类东西不在手时,
  明说「要我落地这条，需要 X」；能自己取的就自己取（如从文件服务按 `storage_key` 拉文件），
  取不到再要。不要把「缺原件」包装成「已定位」。
- **拿不准的要标 UNVERIFIED 并说清要怎么才能定死**（如「需要一次运行态复现插前端请求差异」），
  不要为了看着完整而把推测写成结论。

### 写回源表：走文件交付，不要硬试

用户说「直接写到飞书表的备注里」时，**不要为写回去探路**：多维表格表格视图是 canvas 渲染，DOM 里没有可点击单元格；
记录更新端点也不在前端 bundle 里（`/space/api/bitable/<token>/block_info` 可读 200，但 `/records/update`、
`/records`(POST)、`/record/<rid>` 等全 404）。一次探测无果就转文件交付——继续猜端点/试坐标点击会白烧十几次调用，
且有改错行的风险。真必须自动写回：开着 `page.on('request')` 监听，让用户手动改一个单元格（改完撤回），
从抓到的请求取 URL / header / body 形状再批量写，不要凭路径规律猜。

## Pitfalls

- 不要用 bug 原文的标题代替分析：客户写的标题常是现象，不是改动点，必须落到资源上才有排期价值。
- 「备注」字段有时只有日期（跟进标记），不要把它当方案说明读；有实质方案的备注才引用。
- 同一张表可能有多个视图，用户给的 view 参数决定他看到哪些行；分诊按记录本身做，不要假设视图。
  **统计刷完后要把总数与状态分布打出来核对**（如“处理人含operator-a 50 条”）——条数对不上时先怀疑容器形状、
  参数被拒、或拿的是旧快照，而不是一次就下结论说“表里就这么多”。
- 描述里提到「需求文档」但表里没链接时，直接问用户要哪份文档，不要猜范围。
- 别把「未解决」和「验收不通过」混成一个状态报数——用户是按状态分别跟进的。
- 定位中途发现前面说法错了（如把生成页面归错了），直接显式认错并给修正版，不要辩解；
  用户可能早就知道真实链路（「你刚看的不是吧」就是纠错信号）——他的现场认知优先于你的静态推断。
- **用户反问你的机制解释时（「这个字段指的是源的还是目标的」「为啥会多一个 T」），那就是「你的结论还没到判定级」
  的信号——去取直接证据（读代码的分支条件、读列的 `column_type`、读两边实际存储的值形态），把“推断”落成“读到判定”，
  而不是把同一个结论换个说法重述。重述会被当成没回答。**
- **同一个结论被用户质疑过就要显式撤回并纠正，不要在下一条里默默改口。** 用户自己提出反例/替代方案时，
  先验证他的方案（读代码看能不能成立），确认对就直接说「你是对的，我上一条下错了」并说清错在哪。
- 定位结论里凡涉及跨环境对比（test2 正常、uat 异常），在确认两侧「同名字资源」是否真的是同一份内容之前，
  不要把环境差异归因到某一侧；同名文件/同名模板在不同环境可能就是不同版本。
