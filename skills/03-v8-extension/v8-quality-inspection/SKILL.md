# V8 代码审计与质量巡检

本技能在通用代码审计专家能力之上增加 V8 工作台规则，只增强、不删减。通用审计负责常规安全、功能、性能审查和完整报告；网页端维护的规则是 V8 客开专属的业务扫描规则，或 V8 代码特定使用风险的扫描规则。两类都要执行。远端没有某条公司规则，只表示“未配置”，不能当成代码通过，也不能跳过通用审计。

远端 V8 规则是公司业务约束的来源，不是通用规范的替代。通用标准、语言风险速查、威胁建模、CVSS 评分和报告结构全部保留。通用结论不能替代 V8 资料引用或源码事实；涉及 V8 平台行为拿不准时，用 `search_v8_knowledge` 或源码工具取证，不要编造框架语义。

## 规则获取与范围

1. 先核对审计工作台/MCP 能力。若会话已提供 `get_platform_context`，先调用它；如果没有，不要仅凭 `tool_search` 的一次零命中就断言 MCP/插件未安装，因为工具搜索可能是词法匹配且安装状态与当前会话暴露状态不同。依次查看当前已加载的工具清单，再用只读 `hermes mcp list` 确认服务是否配置/连接；对预期服务用 `hermes mcp test <name>` 确认发现工具。若通用握手失败而服务器提供只读自检/doctor 命令，运行该服务器自检以区分客户端传输故障与服务自身健康。把状态区分为“未配置”“已配置未连接”“已连接但未发现目标工具”“工具可用”“检查受阻/未核实”。安装、启用、健康、工具清单发现、当前会话 schema 暴露、实际调用成功是不同证据，必须分开记录；一个 REA/逆向分析 MCP 健康，不代表 V8 质量规则工具已可用。插件也不等于扫描器：先核对插件 manifest/description 和实际触发面，例如文件写入警告 hook 不能证明它会扫描既有仓库。不得把“本会话当前无法调用”写成“用户机器未安装”。如果检查命令被审批或执行拦截，停止重复尝试，报告“安装状态未核实”，不要改用另一命令绕过。
2. 只在员工本地读取允许审查的 Diff、文件和测试。完整 Diff、绝对路径、凭据和原始日志不得传入 MCP 或持久化。
3. 从文件扩展名、构建文件和依赖判断技术栈。调用 MCP 工具 `get_quality_rules`：React/UDC/TSX 使用 `stack="frontend-react"`；Java、Spring Cloud、Dubbo 或 CIP 服务使用 `stack="backend-java-springcloud"`；混合改动两类都调用。不传 `query`，一次取回该栈全部已启用规则。返回字段使用 `rule_id`、`title`、`description`、`severity`、`stack`。如果服务已连接但工具名未出现在当前目录，先刷新/重载 MCP 工具目录并按服务前缀重新搜索；只有核对服务发现清单后，才能标记“目标工具未暴露”。
4. **远端规则优先**：逐条检查 MCP 返回的启用规则，报告其 `rule_id`、严重度和说明。这些规则只表示 V8 业务闭环或 V8 特定使用风险，不覆盖 OWASP/CWE 常规审计。规则之间不互相替代。
5. 远端规则检查完成后，继续执行下面的通用工程基线，以及本文件后半的完整通用审计。不进行实时外网检索；标准条款以本技能和 `references/` 为准，保持内网可复核。

信息不足时先问，不要假设：

1. 业务定位与数据敏感级别（个人信息、公文、组织、支付、内网核心）。
2. 合规要求（等保定级、行业监管）。未说明时默认 OWASP ASVS L2。
3. 本次是全量、Diff/PR，还是指定模块。大型代码库确认抽样策略：全量、核心模块优先或入口点优先。
4. 是否提供可运行环境。没有运行环境就只做静态审计，并把必须上环境才能确认的项写成验证步骤。

## V8 网页规则怎么用

- 网页「代码检查规则」里新增或修改的内容，就是本技能的 V8 专属规则库。审计开始时以 MCP 实时返回为准，不使用模型记忆里的旧规则。
- 每条命中写成发现，来源写 `V8:<rule_id>`，严重度以规则自带 `severity` 为下限；通用审计若证明影响更高，可以升到 `critical`，并说明理由。
- 规则描述与代码无关时标「不适用」，并写明判断依据。禁止静默跳过。
- 规则要求引用 V8 平台行为时，先查知识库或受控源码，再下结论。查不到则标「待确认」。
- 通用审计发现来源写 `通用审计` 或具体基线名，不要伪装成某个 `rule_id`。

## 通用工程基线

| 类别 | 必查风险 |
|---|---|
| 业务闭环 | 输入、鉴权、状态迁移和失败分支是否闭合；写操作是否幂等；失败后的事务、补偿或可重试边界是否明确；不能把“删除”误实现为不符合业务语义的物理删除。 |
| 异常处理 | 禁止吞异常、空 `catch` 或仅打印后继续成功返回；异常要保留可追踪上下文且不泄露敏感信息；清理、回滚和取消逻辑应在异常路径执行。 |
| 死循环 | 循环、递归、分页、轮询与重试必须有终止条件、上限和推进量；远程失败不能无界立即重试。 |
| 资源释放 | Java 的流、文件、数据库/HTTP 连接、锁、线程池任务应关闭或归还；前端副作用中的事件监听、订阅、定时器、请求和 `AbortController` 应在卸载或替换时清理。 |
| 可用性与宕机风险 | 远程调用要有超时、限次重试和幂等前提；批处理、队列、缓存、集合、分页和并发应受限；识别阻塞调用、无限增长、N+1 查询、资源耗尽和级联放大。 |

只有在代码、Diff 或测试能证明风险时才报告为问题；上下文不足时列为「待确认」或「疑似」，不要虚构缺陷。

## 通用审计专家能力

对代码与架构进行系统性安全、功能、性能三维审查，识别潜在威胁与缺陷，给出可立即落地的修复方案与安全编码示例。每一个发现必须定位到具体代码行或代码块，标注 CWE 编号，引用相关标准条款，并给出 CVSS 4.0 评分。

审计风格严谨、客观、注重证据，绝不臆测。遵循纵深防御与最小权限原则，所有访问控制默认拒绝、显式允许。永不信任用户输入，所有外部输入必须经过校验、转义或参数化处理。

### 必须保留的十项能力

1. **OWASP 十大风险审计**：依据 A01~A10 逐项检查（A01 访问控制含 SSRF、A02 安全配置、A03 供应链、A04 加密、A05 注入、A06 不安全设计、A07 认证、A08 完整性、A09 日志告警、A10 异常处理）。
2. **漏洞检测与修复**：识别 SQL 注入、命令注入、XSS、CSRF、路径遍历、不安全反序列化等漏洞，给出参数化查询、DOMPurify 过滤、参数数组执行等对照修复代码。
3. **认证与授权安全**：JWT 签发与校验（短时效、声明校验、算法固定）、HttpOnly/Secure/SameSite Cookie、OAuth/OIDC 流程（PKCE、state、redirect_uri 白名单）、基于角色与所有权的访问控制、敏感接口限流。
4. **输入校验与密钥管理**：Zod 等模式校验 API 输入、文件上传魔术字节验证、环境变量与密钥托管（Vault/KMS/SSM）、杜绝源码与日志中的密钥泄露。
5. **安全头与依赖治理**：HSTS、CSP、X-Frame-Options、Permissions-Policy 等安全头配置；`npm audit`/`pip-audit`/`govulncheck`/Trivy/Snyk 依赖漏洞扫描与升级策略。
6. **API 安全审计**：OWASP API Security Top 10 2023（BOLA/BOPLA/资源消耗/功能级授权/SSRF/配置/库存/第三方 API）。
7. **LLM/AI 应用安全**：OWASP LLM Top 10 2025（提示注入/敏感信息泄露/供应链/输出处理/过度代理/系统提示泄露/向量弱点/错误信息/无限制消耗）。
8. **性能审计**：算法复杂度、内存管理、并发与锁、数据库与 I/O、缓存策略、云原生资源效率。
9. **功能审计**：需求符合性、业务逻辑、边界条件、异常路径、错误处理、测试充分性、代码质量。
10. **威胁建模**：STRIDE/PASTA/LINDDUN 方法选择，数据流图绘制，信任边界识别。

V8 增强：上述十项一次都不许省略。另外增加第 11 项，V8 网页规则全覆盖矩阵，列出每条 `rule_id` 的命中、不适用或待确认。

## 工作流程

### 步骤 1：信息收集与范围界定

- 明确审计目标：全面审计，还是聚焦某一维度（功能/性能/安全）或特定模块。员工若说代码审计、代码检查、质量检查、v8工作台代码审计或「做代码质量检查」，都进入本技能。默认三维都做，并加 V8 网页规则。
- 获取必要材料：员工本地源代码、Diff 或 PR、架构文档、需求规格、部署环境信息、依赖清单（`pom.xml`、`package.json`、`requirements.txt`、`go.mod` 等）、锁文件与 SBOM（若有）。
- 确定技术栈与框架、运行环境（物理机/虚拟机/K8s/信创环境）。
- 缺失关键信息时主动询问，不要假设。已在对话中给出的范围不要重复追问。

### 步骤 2：架构审查与威胁建模

在逐行审查之前，先建立全局视图：

- 绘制或还原数据流图（DFD），标注信任边界（Trust Boundary）。
- 选用威胁建模方法：STRIDE（外部实体仿冒，数据流篡改或抵赖，数据存储拒绝服务，进程信息泄露）；PASTA（业务视角七步法，适合业务逻辑复杂的系统）；LINDDUN（涉个人信息时使用）。
- 识别关键资产、入口点、信任边界穿越处，作为人工深度审查的优先目标。
- 评估架构级风险：单点故障、故障域隔离、熔断降级、多租户隔离。
- V8 客开额外标出：UDC 页面、手写代码、SPI、Dubbo/Feign、CIP、BPM 回调、组织与公文入口。这些是越权和业务闭环的优先面。

### 步骤 3：自动化扫描（若可用）

- **SAST**：SonarQube、Semgrep、CodeQL、Checkmarx、Fortify。结果仅作线索，必须人工验证。
- **SCA/供应链**：OWASP Dependency-Check、Snyk、Trivy、Grype；生成 SBOM（CycloneDX 或 SPDX）；检查制品签名与来源（SLSA、Sigstore/cosign）。
- **密钥扫描**：gitleaks、truffleHog。检测硬编码密钥、令牌、证书。
- **DAST**（仅当员工提供可运行环境）：OWASP ZAP、Burp Suite。
- **IaC/容器扫描**（若涉及）：Checkov、tfsec、Trivy 镜像扫描。

自动化工具存在误报与漏报，尤其是访问控制。所有发现必须经过人工逻辑验证。内网没有这些工具时跳过本步，在附录写明「未执行，原因：环境无该工具」，然后继续人工审计。不得因为没跑扫描器就拒绝出报告。

### 步骤 4：深度人工审查

逐文件、逐模块审查代码，按三个维度展开，并叠加 V8 网页规则。

#### A. 功能审计（ISO 25010：功能适用性 + 可靠性 + 交互能力）

- **需求符合性**：代码实现是否与需求文档一致，是否有遗漏或过度实现。
- **业务逻辑**：状态机完整性，非法状态转换是否被拒绝，事务边界是否正确。金额、库存、积分等关键计算不用二进制浮点，金额用整数分或 Decimal。幂等性：重复提交、消息重放、重试是否产生重复副作用。
- **边界与异常**：数组越界、空指针（CWE-476）、除零、整数溢出（CWE-190）。输入为空、超长、特殊字符、Unicode（全角、零宽、RTL）。文件不存在、网络超时、数据库连接失败等异常路径。
- **错误处理**：是否捕获应处理的异常，是否吞掉异常（空 catch），失败后系统状态是否一致（OWASP A10）。日志是否包含足够上下文（traceId、用户、参数），且不泄露秘密。
- **测试充分性**：单测是否覆盖关键分支，边界值与负向用例，并发场景。
- **代码质量**：命名、函数长度、圈复杂度（≤10）、重复代码（<5%）、死代码。只有员工明确要求代码质量审计，或问题会导向缺陷时才单列风格问题。

#### B. 性能审计（ISO 25010：性能效率 + 灵活性/可扩展性）

- **算法与数据结构**：O(n²) 及以上能否优化，循环内是否有可提取的不变计算。
- **内存管理**：未关闭资源、静态集合无限增长、监听器未注销、ThreadLocal 未清理、大对象频繁创建、对象池是否合理。
- **并发与锁**：死锁、活锁、竞态（`-race`/ThreadSanitizer），锁粒度与持有时间，线程池参数，goroutine 泄漏。
- **数据库与 I/O**：缺失索引、全表扫描、`SELECT *`、N+1、深分页、批量处理、事务持有时间、连接池、文件缓冲、网络超时与指数退避加抖动。
- **缓存策略**：键设计、失效、穿透、击穿、雪崩，与数据库一致性。
- **可扩展性**：无状态、水平扩展、队列削峰、读写分离。
- **前端性能**（若涉及）：压缩与代码分割、懒加载、DOM、Core Web Vitals（LCP/INP/CLS）。
- **云原生资源效率**（若涉及）：容器 requests/limits、HPA、镜像体积。

#### C. 安全审计（按 OWASP Top 10:2025 组织）

加载 `references/owasp-top-10-2025.md` 获取每类详细检查项。

**A01 失效的访问控制（含 SSRF）**：水平/垂直越权（CWE-639/862/863/284）、SSRF（CWE-918，禁内网、元数据地址、DNS 重绑定）、路径遍历（CWE-22）。服务端独立校验授权，默认拒绝。

**A02 安全配置错误**：调试模式、Swagger、Actuator 暴露、CORS 过宽、安全响应头缺失、默认凭证、云存储权限过宽、IaC 错误配置。

**A03 软件供应链失效**：依赖 CVE、锁文件、SBOM、制品签名、CI/CD 管道完整性、私有源可信性。

**A04 加密失败**：弱算法（MD5/SHA1/DES/RC4）、密码哈希（bcrypt≥12 轮、scrypt、argon2id 加盐）、TLS 1.2+、AES-256-GCM 落库加密、密钥来源（KMS/Vault）、安全随机源（SecureRandom/secrets）。

**A05 注入**：SQL 注入（CWE-89，参数化查询）、命令注入（CWE-78/77，参数数组）、XSS（CWE-79，上下文编码）、LDAP/NoSQL/模板/表达式/日志注入、XXE。

**A06 不安全设计**：防重放、防篡改（签名）、频控与风控、服务端校验（不依赖前端）。

**A07 认证失败**：密码策略与存储、登录防爆破、MFA、会话管理（≥128bit 熵、HttpOnly/Secure/SameSite、登出后服务端失效）、JWT（算法固定、短时效、声明校验、撤销）、OAuth/OIDC（state、redirect_uri、PKCE）。

**A08 软件和数据完整性失败**：不安全反序列化（CWE-502）、未验证的更新、CI/CD 完整性。

**A09 安全日志与告警失败**：认证、授权、管理操作日志，日志元数据（UTC 时间、用户、IP、traceId），防篡改，告警阈值，敏感数据脱敏（CWE-532）。

**A10 异常条件处理不当**：fail-open、吞异常、错误信息泄露、降级路径安全性。

专项检查（加载对应参考文档）：

- **API 安全**（`references/owasp-api-security-top-10-2023.md`）：BOLA、BOPLA、资源消耗、功能级授权、SSRF、配置、库存、第三方 API。
- **LLM/AI 应用**（`references/owasp-llm-top-10-2025.md`）：提示注入、敏感信息泄露、供应链、输出处理、过度代理、系统提示泄露、向量弱点、错误信息、无限制消耗。没有大模型调用时注明「本范围不涉及 LLM」。
- **秘密管理**：全库扫描硬编码密钥，密钥轮换，`.env` 入库检查。发现秘密只记类型和位置，不把秘密正文写入报告或 MCP。

### 步骤 5：验证与风险评估

- 对每个疑似问题构造攻击路径或压力场景。环境不允许时标注「疑似」或「待确认」，并给出验证步骤。
- **CVSS 4.0 评分**：逐条基于明确攻击前提、权限、用户交互、机密性/完整性/可用性影响构造基础向量，并用 FIRST 官方 CVSS 4.0 Calculator 或经验证的本地实现核分；报告保留向量串与分值，再结合业务上下文定级。禁止给不同发现套用同一组“模板分”、凭印象填分或把工程严重度当 CVSS。若无法核验计算器/向量，将分值标为“待核”，不要伪造数字；V8 规则命中同时保留规则严重度。
- 定级：**严重 Critical（9.0~10.0）/ 高 High（7.0~8.9）/ 中 Medium（4.0~6.9）/ 低 Low（0.1~3.9）/ 信息 Info（0 或不适用）**。
- `critical` 用于可能导致宕机、数据严重损坏或大范围安全事故的直接证据。其余严重度遵循远端规则，或按实际影响谨慎标注。
- 对 Critical/High 给出建议修复时限。Critical 建议 24~72 小时内修复或下线缓解。

### 步骤 6：报告生成

默认使用中文。主产物是一份单文件 HTML，不要只在对话里贴 Markdown。

文件只写到当前用户的下载目录，禁止写到项目 `out/` 或仓库里：

- macOS、Linux：`~/Downloads/代码审计报告-<对象>-<YYYYMMDD>.html`
- Windows：`%USERPROFILE%\Downloads\代码审计报告-<对象>-<YYYYMMDD>.html`

对话里只给这个绝对路径、一句结论和最高的三条风险，不把整页 HTML 贴进对话。

版式必须从 `references/report-template.html` 起稿。严重级别徽章只用 `sev-critical`、`sev-high`、`sev-midhigh`、`sev-mid`、`sev-low`、`sev-info`。原样保留其中的 `<style>` 和文末目录高亮脚本，只替换文字和数字。不要另起一套 class，不要改成深色封面，不要拿图表库。

封面是浅色，不是深蓝底白字。标题下一行写范围和规模，句式为：`模块甲 · 模块乙　|　约 N 个文件 / M 行`。文件数和行数按实际阅读到的源码统计，不要留空，也不要写死示例里的 120 和 32000。再下一行是量化结论，句式固定为：`审计已完成　共 N 项发现，其中 P0 发版阻断 M 项`。有阻断项时圆点用红色，没有时用绿色 `dot ok`。封面底部元信息用示例里的「标准映射」，写本次实际引用到的标准，例如 `标准映射　OWASP Top 10:2025 · CWE Top 25 · OWASP API Security 2023`。不要写「审计方式」或「人工审计 + V8 工作台规则」。

「模块 × 严重性分布」是堆叠条，不是一根单色总数条。每个模块一条 `.mbar`，里面按严重、高、中高、中、低、信息放 `.seg`。`flex` 等于该级别的数量，颜色只用模板里的六个色值。数量为 0 的级别不画色块，图例里也不写。条本身拉满，用色块比例表示构成。右侧环形图用 `conic-gradient`，三段百分比必须等于安全、功能、性能的真实占比，中心数字是发现总数。

左侧目录不能省。使用模板里的 `.sidebar`，二级用 `toc-l2`，三级用 `toc-l3`，`href` 指向正文标题的 `id`。目录随页面滚动固定，并用模板脚本高亮当前节。

目录按模块分章，和示例报告一样。每个模块单独成章，章名带该模块的发现总数，例如 `二、加密与档案 SPI（17 项）`。章下面严重和高危合并成一节，其余按档分开，并带数量：`2.1 严重/高危（3）`、`2.2 中（6）`、`2.3 低（8）`、`2.4 信息（1）`。某一档是 0 就不出现。模块末尾有源码能证明的正面写法时，再加一节积极发现。

不要把所有模块收成一章「分模块发现」。同一类问题出现在不同文件或不同模块时分开写，低危和信息项也逐条保留，不要因为“类似”就收成一条。api、service 这种代码分层不要当目录。

其余菜单仍按示例：一、发现总览（1.1 矩阵、1.2 维度、1.3 Top 风险），然后是各模块章，再是跨模块共性问题、修复优先级与运行时验证、审计质量声明、总体结论与整改路线、附录。

写完 HTML 后先在本地打开检查，不合格就改完再交给员工：

- 所有表格都放在 `.table-wrap` 里，使用模板的 `table-layout:fixed`。单元格允许换行，禁止 `white-space:nowrap`，禁止表格画出白色内容卡片。
- P0 表只放五列：编号、模块、位置、问题、CVSS。CVSS 列只写分数，例如 `7.5`，不写向量串，不写「规则下限」。问题列用一句话。路径放在位置列，过长就换行，不要把列撑出卡片。
- 封面能看见文件数和行数，以及「审计已完成　共 N 项发现，其中 P0 发版阻断 M 项」。
- 每个模块目录都带总数。模块内是 `严重/高危（3）`、`中（6）`、`低（8）`、`信息（1）`。严重和高危放在同一节，但条目仍分别用严重、高危徽章。
- 页脚只写一行：`报告标题 · 只读静态审计，未修改任何被审计文件 · 所有发现均附源码行号`。不要在页脚写「严禁复制到生产代码」。

章节顺序与示例报告一致：

1. 发现总览：严重性矩阵、维度分布、P0 表。
2. 按模块分章。每章内按严重/高危、中、低、信息写明细，标题带数量。有就写积极发现。
3. 跨模块共性问题。每条写清它在哪些模块、哪些文件重复出现。
4. 修复优先级和运行时验证清单。优先级按 P0、P1、P2 分阶段，写建议完成时间和改哪些编号。运行时验证逐条列出还要上环境确认的权限、网关和事务。
5. 审计质量声明必须有四块：分模块覆盖表（模块、范围、文件数、行数）、未覆盖范围及原因、对不上源码所以没收录的说法、合并去重和统计口径。没有排除项时写「本轮没有剔除项」，不要整节省掉。
6. 总体结论、分阶段整改路线，以及正面范式。正面范式只写本轮源码里已经做对、可供其他模块照抄的写法。
7. 附录：V8 规则覆盖矩阵。每条 MCP 规则都要有命中、不适用或待确认。

发现标题写成 `编号 + 徽章 + 短标题`。每条发现都要写全这些，缺一项就不算完成：位置、证据代码、攻击路径或触发条件、业务影响、标准映射、修复建议、运行时验证、测试缺口。CVSS 4.0 仅在基础向量和分值经官方计算器/已验证实现核算后填写；无法核算时明确标“待核”，不得编造分值或向量。低危也按这个结构写，只是可以更短。正文先说代码在做什么，再说因此会怎样。不要堆「本次无」「必须」「严禁」这种模板句。

# 代码审计报告

### 步骤 7：复测与闭环

- 修复完成后对每条发现做回归验证，输出复测结论：已修复、部分修复、未修复或风险接受。报告生成前重新核对当前源码和测试，把审计基线中的旧发现逐项标记状态，不能把已修复问题继续计入未关闭总数，也不能把“测试通过”误写为“真库验证通过”。
- 覆盖文件数、行数、发现数、严重度和维度分布必须从结构化审计结果程序化统计；先按规范化仓库相对路径去重，再汇总，避免多条审计流重复计数。报告封面、矩阵、模块章节、目录、Top 风险表的数字必须互相一致。
- 建议把本次检查要点沉淀为 CI 门禁（SAST 规则、依赖扫描、密钥扫描、质量阈值）和网页规则库里的新 `rule_id`。员工确认后再建议管理员入库，不直接改规则库。

## 输出与沉淀

- 完整报告是本次主产物，必须按 `references/report-template.html` 落成下载目录里的单文件 HTML。对话里只给路径和结论。

## 审计原则

1. **证据驱动**：每个结论必须关联到具体代码，绝不发表无根据的猜测。
2. **避免误报**：自动化工具结果必须手动确认。不确定的问题标注「疑似」并给出验证步骤。
3. **可操作建议**：修复建议必须具体、可落地，提供错误示例和正确示例，注明安全机制。
4. **优先级明确**：聚焦真正的高风险问题，避免陷入琐碎风格问题，除非员工明确要求代码质量审计。
5. **标准时效性**：引用标准必须核对版本。报告注明引用版本，避免映射到已废弃类别编号。
6. **AI 生成代码**：AI 辅助编码产出同样审计，额外关注逻辑正确性、幻觉 API、许可证污染和依赖引入是否合理。
7. **保密与伦理**：源代码和数据只用于本次审计。漏洞细节按最小披露原则传递，不把秘密写入报告、MCP 或知识库。
8. **纵深防御与最小权限**：访问控制默认拒绝、显式允许。系统须安全失败，生产环境关闭调试模式。
9. **报告中的漏洞示例仅供教学对照，严禁直接复制到生产代码。**
10. **涉及命令或敏感文件改动时，明确提示人工复核后再应用。**
11. **依赖审计命令与敏感文件改动，须由用户在受控环境中审慎执行并复核。**
12. **V8 规则与通用审计并存**：网页规则命中不能抵消通用高危发现；通用扫描干净也不能抵消 V8 规则命中。
