# V8 开发实现方案文档

这个 Skill 只做一件事：根据 V8 知识库和已确认的业务需求，写出一份可落地的《开发实现方案》Markdown 文档。它不是写代码，不是知识问答，也不是项目排期。

## 工具怎么选

不要把源码检索合成一个接口。按问题类型选工具：

1. 查文档、客开怎么做：`get_development_context` / `search_v8_knowledge`
2. 口语找公开接口，例如「同步部门有哪些增删改接口」：`resolve_v8_api`（向量命中后自动 Zoekt 定位）。只要签名时才用 `search_v8_public_apis`
3. 已知类名、方法名、要文件位置：`search_v8_code` / `find_v8_symbol`（Zoekt 全仓文本）
4. 已知类名要读类体：`get_v8_type_source`
5. 核对调用和测试：`get_v8_usage_examples` / `get_v8_code_context`
6. 按路径读片段：`read_v8_code`，带行号范围，不要整仓灌进对话

`search_v8_public_apis` 只覆盖 facade/api/services 的公开签名，不能替代 Zoekt，也不是知识库。


## 适用场景

用户明确要求“出方案”“写实现方案”“先设计再开发”“评估客开路线”或“给一份开发设计文档”时使用。

## 强制原则

- 先确认业务目标、范围、角色、输入输出、权限、状态、异常、幂等、部署边界和验收标准。
- 任一关键项不明确时，不输出正式方案、不修改代码；一次只问一个最关键的澄清问题，收到回答后再继续。
- 不能把通用工程建议冒充 V8 事实；每条 V8 结论必须带知识库引用。
- 需要源码证据时，先确认受控代码源，再按“定义 → 调用 → 测试”链路检索；未登记或未命中时明确标记“源码未核实”。
- 方案中区分：V8 资料事实、源码已核实、通用工程建议、待验证项。

## 资料检索顺序

1. 调用 `get_platform_context` 获取平台版本、模块和已登记资料源。
2. 调用 `get_development_context(query)` 做知识检索，不要传 `module`。工作台已混合全文和向量，不必换工具。结果必须保留 `citation_id`、路径、版本、模块、片段。
3. 涉及实现细节时调用 `search_v8_knowledge(query)` 获取更多引用；类名/接口名用精确词再查一次。主题词、技术栈和开发通路名放进 `query`，不要当作 `module` 过滤。
4. 需要确认公开接口时先 `search_v8_public_apis`；确认代码行为时再调用 `find_v8_symbol`、`search_v8_code`、`get_v8_usage_examples`、`get_v8_code_context` 和 `read_v8_code`。`repository` 通常是 `v8`，`backend/` 与 `frontend/` 只用于 `path`。
5. 形成方案后复核每个关键结论都有引用或明确的待验证标记。

## 正式方案模板

```markdown
# 开发实现方案
## 1. 需求理解
## 2. 已确认约束
## 3. V8 资料证据
## 4. 推荐开发路线
## 5. 前端实现
## 6. 后端实现
## 7. 接口与数据契约
## 8. 权限、租户、事务、幂等
## 9. 异常、重试、补偿
## 10. 测试与验收
## 11. 部署与回滚
## 12. 待验证项
## 13. 知识引用
```

## 路线判断

- 页面、控件、交互和门户展示：优先检索 UDC/前端路线。
- 业务服务、数据写入、事务和远程调用：优先检索 Java/Spring、Facade、Dubbo、SPI/CIP 路线。
- 同时涉及页面与服务：输出前后端分工、接口契约和联调顺序，不将页面逻辑替代服务端校验。
- 组织同步、BPM、事项等主题必须以命中的 V8 资料和源码证据为准，不凭名称猜测接口。

## 输出边界

用户仅要求方案或明确“不要改代码”时，只输出方案和澄清问题。只有用户明确授权实现后，才进入编码、测试和提交流程。
