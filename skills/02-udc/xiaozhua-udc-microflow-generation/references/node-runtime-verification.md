# 节点运行时验证（把 SCHEMA_VERIFIED 推到 RUNTIME_VERIFIED）

适用于要给某个微流程节点补「真实执行且业务结果正确」的证据时。
没有这套顺序，最容易得到的是「构建成功 + success=true」这种看起来像证据、
实际什么都证明不了的结果。

## 0. 先定「这个节点要证明什么」

写验证脚本前先用一句话写清断言。模糊的断言（「节点能跑」）最后一定退化成
`success=true`。可验收的断言都长成「某张表的某一列出现了某个可预测值」。

## A. 语料审计（先数，再看）

原始 dump：`scratch/pmp_schemas.json`（643 条 RELEASE 流程 / 7937 个节点，发布态）。

```python
# 按 actionType 收样本，注意走 conditions[].nodes 与 nodes 两路
sub = [(mid, n) for mid, rec in dump.items() for n in walk(rec["ds"]["nodes"])
       if (n.get("actionType") or n.get("type")) == TARGET]
```

必须统计的六项（少一项就会在写构造器时猜）：

| 维度 | 为什么必要 |
|---|---|
| 引用方式（对象结构） | 决定构造器要拉哪些活引用 |
| 入参形态与类型分布 | 决定走哪条映射分支（标量 vs DTO vs 列表） |
| 出参形态与类型分布 | 决定下游怎么引用 |
| 传参字段名（`value`/`attrs`/`mappingType`） | 写错字段名时平台常静默忽略 |
| 有无参/有无出参的组合占比 | 直接暴露「只实现了少数形态」 |
| 变更后的契约关系 | 决定属性刷新怎么验 |

**规则一：文档里的样本数会漂，必须从 dump 重数。**
实测过能力矩阵写 706、实际只有 251 —— 而样本数错了通常意味着当初的形态归纳也偏了。
新旧差异本身就是信号，别当排版问题忽略。

**规则二：区分「有平台证据的形态」与「只有静态样本的形态」。**
手工搭的验收流只证明字段存在，不证明取值正确（同一份样本里可能同时存在
写错的 `type` 和平台必填但为空的字段）。统计结论要标注证据来源。

## B. 自建隔离对象

优先选**不依赖外部业务对象**的验证形态：

- 能自建父/子流程的节点（子流程调用、子流程事件）→ 建两条临时流程
- 能自建实体的节点（增删改查、批量）→ 用测试实体 + 唯一标记
- 列表类节点 → 同一流程内造列表、改列表、把结果落库

标记值要**固定、可预测、可回读**，并带唯一后缀（时间戳尾号），
保证能精确清理，不会碰到历史数据。

**SQL 造种子数据的三个必填列（缺一个就白跑一轮）**：

```sql
INSERT INTO <物理表> (id, task_id, ..., tenant_id, creator, create_time, update_time)
VALUES (<显式雪花id>, '<MARK>-M', ..., <应用租户>, -1, NOW(), NOW())
```

- `id` 不是自增列：不给值会报 `Duplicate entry '0' for key 'PRIMARY'`。用 77xxxxxxxxxxxxxxx 段造。
- `tenant_id` 必须是**应用租户**（抄一行平台写入的行），填 0 时平台查询一条都查不到，
  现象与「条件失效」一模一样。
- `creator=-1` 与平台写入行一致。

**一个动作一条流程，不用一种形态推导另一种。** 同一条流程里串多个待验动作，
任何一个失败整条回滚（见单事务铁律），取证节点一起丢；而且「CLEAR 通过」不能推出
「REMOVE 通过」——四个动作的 dataSource 形态完全不同。单轮成本约：构建 4 分钟 + 等调度 5 分钟。

### B2. 种子要造在流程里，不要依赖外部 SQL（实测两次被清）

应用里**别的流程会清这张表**：外部 SQL 插好的 3 行种子，在下一轮执行前就没了，
于是聚合类断言全返回 0（SUM/MIN/MAX/MAP 都是 0），看起来像「节点没生效」。
同一现象在不同轮次出现过两次（一次种子整批消失，一次只剩自己的 4 行）。

做法：把 `CREATE_ENTITY` 造种子的节点**放在被测流程最前面**，紧接查询/运算节点，
整条流程一个事务。这样即使表被别的流程清过，本轮的数据也一定自洽。

### B3. 过滤类断言必须自带隔离条件

只写 `processedRows > 1 && processedRows <= 3` 这种「业务条件」时，会把表里
**别的流程留下的行**一起算进来——实测造了 4 行、断言返回 6。
每条过滤/多条件断言都要额外带一条 `sourceTable = <本批标记>`（或等价的自有唯一列），
返回数才等于「本批数据的子集」，否则数字无意义。

**多条件的另一半坑**：多个条件写成 `[GROUP{conditions:[...]}]`（1 个 GROUP 内 N 个 CONDITION），
不是多个 GROUP 并列（语料 170/170，多 GROUP 会回 `BOOT_1001 Parameter Error` 无明细）。

**安全边界写进脚本注释**：为什么这个对象跑不出业务副作用（如「源实体 0 行，
规则跑不到任何记录」）。评审的人要能一眼看出边界。

## C. 调用链验证

分步顺序固定（顺序反了会拿到假错误）：

1. 建被调方（子流程/目标对象）→ 回读确认参数真的落库（`ds.input` / `ds.output`）
2. 发布 → 构建到 RELEASE（被引用方必须 RELEASE，DRAFT 不可被引用）
3. 建调用方 → 组装调用节点 → 发布
4. 构建 → 等调度/触发执行
5. 读侧取证

**同流程自证**优先于跨流程比对：对照支路和实验支路放在同一条流程里，
一次执行就能得到两个数字（例：对照循环 3 行 : 实验循环 1 行）。
跨流程比对要跑两轮，任何环境差异都会污染结论。

**用「谁写的」区分两行**：当父/子都往同一张表写时，让它们写进**不同的列**或
不同前缀的值，再靠时间戳顺序确认调用方向（子先写、父后写，间隔应为毫秒级）。

## D. 属性刷新（引用关系变更后必须验）

被引用对象的契约一改，调用方存的副本就过期了。这里有两个反直觉的平台行为：

1. **单流程发布会放行。** 调用方再次 `publish` 时平台只做本流程的结构校验，
   不做全局契约比对。
2. **构建期才拦。** 触发构建会在十几秒内 FAIL，报「一致性检测未通过」
   （`AbstractDeployService.doParallel`）。

比对规则（`MicroFlowComponentUtils.checkMfService`）：

```java
compare(source, target) = dataType 相等 && type 相等 && (source.id 为空 || id 相等)
```

**只比 dataType / type / id** —— 改描述、改名字不会触发，必须改**类型或结构**才能复现。

验证步骤：

1. 改被引用方契约，保存 + 发布
2. 调用方**不刷新**直接发布 → 记录它居然通过（这本身就是结论）
3. 触发构建 → 必须 FAIL，把报错原文记下来
4. **刷新 = 重新读取被引用方当前定义，重建调用节点**（新建活引用实例以清缓存）
5. 发布 → 构建 → 再跑一轮 → 读侧必须看到新契约的值

**禁止用「重新 POST 一遍旧调用节点」冒充刷新**：`mfService` 不变时第 3 步会一直挡着，
这正好可以当作反证——刷新前必红、刷新后必绿。

## E. 结果断言表

每类节点至少要能回答这几问，且每一问都对应一条读侧查询：

| 问题 | 判据 |
|---|---|
| 被调方真的收到了入参吗 | 被调方写下的值 = 调用方传入的值 |
| 被调方的处理逻辑跑了吗 | 被调方自己的副作用可见（新增行/计数变化） |
| 返回值是对的吗 | 调用方写下的值 = 被调方声明的返回值 |
| 下游真的用了返回值吗 | 返回值出现在下游节点的产物里，不只是被接收 |
| 失败路径真的失败了吗 | 用 `CUSTOM_ERROR` / 故意违规值做负向对照 |

**不能只验正向**：正向证明「能跑」，负向证明「判据有效」。

## F. 定级与落库

| 拿到的证据 | 定级 |
|---|---|
| 闸门过 + 构造成功 | CONSTRUCTED |
| publish `check=true` / `errors=[]` | SCHEMA_VERIFIED |
| 构建 SUCCESS | BUILD_VERIFIED |
| 部署并触发执行，但无可观测副作用（无订阅者的事件等） | LIVE_EXECUTED |
| 读侧数据满足 E 表全部断言 | RUNTIME_VERIFIED |

定级后三处同步：`core/facts/udc/microflow/<节点>.md`（机制 + 实测 + 未覆盖）、
`capability-matrix.md`（状态 + 样本数）、本技能 `references/`。
**样本数变了要重算实例加权覆盖率，别手填百分比。**

## G. 收尾

顺序不能省，少一步就会持续长出新数据：

```
删调用方 → 删被调方 → 清测试数据 → 再构建一次 → 等满一个周期 → 复查为 0
```

删流程**不会**停掉已注册的定时任务（`ctp_job_*` 标了 `is_delete=1` 也照跑），
必须再构建一次让应用包里不再包含它。复查要求：清完后过一个完整调度周期，
行数仍是 0。

## 常见退化

| 退化 | 表现 | 纠正 |
|---|---|---|
| 把 success 当结果 | 日志全绿，业务值不对 | 判据只写读侧 SQL |
| 只验入参不验出参 | 调用方拿到 null 也算通过 | 出入参各一条读侧证据 |
| 用旧缓存读契约 | 改了被引用方，调用方仍读到旧形态 | 新建活引用实例 |
| 只删流程不清数据 | 下一轮又长出新行 | 按 G 步走完 |
| 语料数与文档不一致还照用 | 形态归纳系统性偏移 | 从 dump 重算并记录差异 |
| 外部 SQL 种子被别的流程清掉 | 聚合全 0，误判「节点不生效」 | 种子造在流程内，同一事务自洽 |
| 过滤断言不带自带隔离条件 | 返回数大于本批数据量（别人行被算进来） | 每条断言加 `sourceTable=<本批标记>` |
