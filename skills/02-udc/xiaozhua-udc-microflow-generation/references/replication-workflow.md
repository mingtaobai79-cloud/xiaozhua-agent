# 复刻对方应用的业务到本应用

场景：用户给一个「参考应用」（如智能项目管理平台），要求把里面的真实业务在我们自己的应用里复刻并验证。
原则：**参考应用只读**，写操作只发生在自己这边。

## 1. 选料（只读）

从已落地的语料快照里按触发类型分组挑流程，不要现场去对方环境拉：

- 第一轮挑 **3–6 个节点、不含 SUB_MICROFLOW / CALL_APP_SERVICE** 的 MANUAL 流程，先把主链跑通；
- 定时（SCHEDULE）、事件（BUSINESS_EVENT）各至少一条；
- 语料里常见的四类真实业务形状，直接可作模板：
  * `RETRIEVE → BRANCH → CHANGE_ENTITY`（查一条 → 判断 → 改）
  * `RETRIEVE_ARRAY → BRANCH → CUSTOM_ERROR`（查一批 → 校验 → 报错）
  * `CREATE_LIST → FOR_EACH → CHANGE_VARIABLE/CHANGE_ENTITY`（批量改）
  * `CREATE_VARIABLE → RETRIEVE → CHANGE_VARIABLE`（取数 → 落变量）

读流程时同时记下：trigger 类型、节点序列、涉及的实体、出入参形态——这四项决定能不能在本应用复刻。

## 2. 业务对齐（先映射，再写码）

1. 把对方实体/字段映射到本应用已有实体；结构可复用，**值不可复用**（实体 id、字段 id、relationEntity、md5 都必须取本应用的）。
2. 对应不上的部分列出来：需要新建实体 / 自定义对象 / 枚举。
3. 业务语义不等价时改写成等价业务，不要硬搬节点顺序——节点是为业务服务的。

## 3. 本地补齐（缺什么建什么）

- 实体 / 字段 / 枚举 / 自定义对象都在**本应用**建，走 setting 域，不碰参考应用。
- 新建后立刻回读一次元数据，确认 `relationEntity`、字段 `attrType`（16 键）都能取到，再拿去生成。

## 4. 生成与自证

按 SKILL.md 的主流程：契约表（G23）→ 构造器 → G1–G23 闸门 → publish → `prove()` → DELTA 构建。

验收标准（缺一不可）：
- `publish.errors == []` 且状态回 `RELEASE`；
- `prove().ui.ok == True`（无 `isCompleted=false`、无抽屉红字）；
- 有参流程的 PARAM 页签参数名回显非空；
- `detection_mine == []`（应用级检测里属于本流程的条目为零）；
- `backBuild.log` = `BUILD SUCCESS`、Java 报错 0。

## 5. 失败归因（别算错账）

- **应用级一致性检测会混入既有资产的问题**：循环内调服务的警告、生单规则映射、选项集缺项，都可能不是新流程造成的。先按流程名/id 过滤，再把剩下的当自己的问题查。
- 检测项属于别人的资产时，它会**拦住整个应用的构建**；这时「没拿到编译结论」要如实说，不能拿上一轮的构建结果冒充。
- 构建接口返回 `UDC_DEPLOY_0002 app publishing` = 有部署占着锁，等锁释放或停掉旧部署再发，**不要并发重试**。

## 6. 事件类复刻的坑

事件是**唯一绑定**：某事件被一条流程监听后，就不再出现在 `udcMicroflowFilterEventPost` 候选列表里。复刻事件类业务前先看本地还剩哪些可用事件；没有就改已有流程，不要新建一条监听同一事件。

## 7. 一轮的交付形态

一次复刻轮次交：N 条流程 id + 各自的 prove 结果 + 构建结论 + 一条「哪些还得补」的清单。汇报只说实测结论，不写过程叙事。
