# 低代码在线生成 Word 模板诊断与修复

## 渲染机制（先懂这个再动手）

- 平台「单据转文档」按**实体字段 caption** 建变量表：`udc_test2.udc_attribute.caption`（用 entity_id 锁定实体，业务表在 `znxmglpt*_uat` 库）。
- 模板占位符 `${中文名}` 与 caption **逐字符精确匹配**——`其它`(U+5B83) ≠ `其他`(U+4ED6)，肉眼同义但字节不等。
- 不匹配时**静默替换为空**，不报错。DB 有值、微流程映射正确、文档该处却空白 ⇒ 首先怀疑占位符与 caption 差一个字。
- test2/UAT 两环境各自绑定**不同版本**的模板文件：test2 正常 UAT 不正常时，先 diff 两侧 `ctp_file` 同名模板的 md5/大小，不要假定是同一份。**同一环境同一天也可能并存多份**（同一模板名对应多个不同 md5 = 在反复上传），先按 `create_time` 取最新那份再比。
- 文件指纹之外还要比**模板配置行的其余列**：同一模板名在两端 `htmbpzb_<id>` 里，`version`、`update_time`，以及 `mubanleixing`、`jiaohuofangshi`（可选枚举集合）、`mfgzbq`（买卖双方盖章文字）、`sfwjwht` / `sfbhxmysjsh` / `sfbhazds` 等扩展列为空还是已配，直接反映「这一端到底配没配过」。一端全是空壳（`version=0`、扩展列全空）而另一端已配满，是典型的环境漂移——报告里要点出这层，别只报「模板文件不一样」。

## Procedure

1. **只读定位**（不改任何东西；产出定位报告，用户点头后才改——这是铁律）：
   - **先分流**：对每个可疑字段跑取值分布（`COUNT(*)` 与 `SUM(字段非空)`）。`有值行=0` = 取值链路没填，去查表单/拼接微流程；`DB 有值但文档空白` = 才走占位符与 caption 比对。SQL 与表结构见 `references/contract-template-evidence.md`。
   - bug 源读取与页面↔微流程反查：见 `feishu-bitable-cdp-extract` skill 坑列表（udc_test2 元数据库、数字 id 反查）。
   - DB 取证（pymysql + xiaozhua-low-code-environment/.env，只读）：业务表实际值、`ctp_enum_item` 选项、`ctp_file` 文件指纹。
   - 解包用户给的模板 docx：`zipfile` 读 `word/document.xml`，run 拼接后正则列出全部占位符及出现次数。
   - 输出「现象 → 根因 → 改哪侧（模板 / 字段 caption / 枚举 / 微流程）」对照表。
2. **诊断归类**：模板占位符/字体形态表见 `references/docx-run-surgery.md`；附件上传/删除权限类 bug 的定位与修复模式见 `references/attachment-permission.md`；合同模板取证的表/列/查询骨架（取值分布分流、caption 码点对比、模板文件与配置行指纹、配对字段）见 `references/contract-template-evidence.md`。
3. **run 级修复**（python：zipfile 解包 → 改 document.xml → 重打包）：配方与坑见 `references/docx-run-surgery.md`。修复脚本落盘留档。一字节/单句类小改动优先用「锚完整 run 的精确替换 + 命中数断言」，别为了修一个字把全量拆散合并也裹进来。
4. **校验全过才交付**：占位符总数与源一致、无独立 `${`/`}` run、无重复标点、模拟替换无残留、XML 标签开闭计数与源一致。
5. **交付到桌面**：建专目录，含修复成品 docx、原始备份 docx、fix 脚本；删除废版中间产物避免误传 UAT。

## Pitfalls

- **先定「哪个实体是活的」，再谈 caption。** 同一业务字段在多个实体上存在副本（复制页面/复制链路各一套），
  caption 还可能在不同实体上分别是 `其它`(U+5B83) 和 `其他`(U+4ED6)。**不要拿全库 caption 去比对模板**——
  先按 `udc_attribute` 的 `entity_id` 分组，统计每个实体上该字段的 caption，再用页面的数据源/实体绑定
  确定真正取数的那一个，只比它。否则会得出「字段存在所以不是这个问题」的假结论。
- **症状确认：渲染出「空白槽」而不是报错。** 报告中写「品质服务其他补充未生成」的，截图里常是一个空括号/空槽
  `【 】`——这就是占位符与 caption 差一个字的静默置空表现。看到空槽先查异体字，不要先去查取数逻辑。
- **模板是 `.doc`(OLE) 与 `.docx` 并存，先经配置表定位实际绑定件。** 模板配置表 `htmbpzb_<id>` 的
  `mubanmingcheng`（模板名）→ `ctp_file` 同名多版本行（按 `create_time` 取最新），`storage_key` 指向
  OSS 文件。占位符检查必须拿真正的文件内容；`.doc` 二进制无法直接正则，优先取同上的 `.docx` 版本，
  或让用户给原件。
- **生成实体里的 `mubanmingcheng` 存的是 id 不是文件名。** `htmbzxsc` 这类「在线生成」实体的该字段存模板 id（20 位长整数），不是 `htmbpzb.mubanmingcheng` 里的文件名——按模板名去查记录会得到 0 命中，极易误判成「这个模板没人用过」。要按模板定位记录：先从 `htmbpzb` 用名字取到那行的 id / 关联字段，再按 id 查，或直接让用户给单据流水号。
- **占位符有两级形态 `${实体}{字段}`，解析时必须两级分开。** 单级正则 `\$\{[^}]{1,40}\}` 在第一个 `}` 就停，`${扩展信息}{品质服务其它补充}` 只会匹配出外层 `${扩展信息}`，内层字段名一次都不出现——照这份清单比对会得出「模板里没这个字段」的假结论，恰好把真根因漏掉。两级里**内层字段名才是参与 caption 匹配的那个**，外层只是路径前缀。诊断/计数脚本与两级合并集的校验清单见 `references/docx-run-surgery.md`。
- **先查「记录里到底有没有值」，再怀疑模板占位符。** 对可疑字段做一次取值分布（`SELECT COUNT(*) … WHERE <字段> IS NOT NULL AND <字段> <> ''`）：**有值行=0 说明取值链路压根没填**，此时改模板占位符是白做——问题在表单、拼接微流程或默认值，不在文档渲染。只有「DB 有值但文档空白」才走占位符与 caption 逐字符比对那条路。两条分支修法完全不同，先分流再动手。
- **同一个字段会同时存在于十几张表；“填写的那张表有值、模板取数的那张表 0 行”是第三条分支。** 先 `information_schema.columns` 按列名找全命中表，再逐表数非空行；两级占位符的外层实体名就是「模板从哪张表取数」的权威答案，只拿那一个实体的 `table_name` 下结论。断链时间用**同名历史备份表**（`<表>_backup_<epochMs>` / `<表>_bak_<YYYYMMDD>`）取证：备份有值、现表为 0 = 断在哪。报告里必须把「改模板外层实体」与「改写入侧落库逻辑」两个分支都列出——它们可以同时成立，只修异体字会看起来「修好了」而渲染仍空。
- **字段恒空可能是有意设计，先看它旁边有没有配对字段。** 备注类字段常是「按钮 + 文本」两段式（如 `xbeizhuanniu1` / `xbeizhuanniu2` / `xbeizhuwenben`），值由按钮拼进文本字段，主字段本身就一直是空；开关/下拉类常是「枚举 + 文本」配对（如 `jiaohuofangshi` + `jiaohuofangshimeiju` + `jiaohuofangshiwenben`），**只有某几种选项组合才会正确拼出文本**——「全选对、单选错」的报障优先查这一对，它是拼接口径问题，不是模板问题。
- **先确认是哪条生成链路再下结论**：平台有两条并行的在线生成链——合同申请单内嵌（实体=合同档案）与合同文件管理独立单据（实体=htmbzxsc，页面 zxscdjzwdxq）。用页面 schema 里的微流程数字 id 反查承载页面，别凭 caption 相似推断。
- **两条链的同名拼接微流程不是「复制件」，它们绑不同的实体与页面——先读出各自写哪张表，再谈同步。** 实测两条 `交货备注拼接` 的节点图逐节点相同（同 nodeId 序列、同 8 个开关分支、同一个 `SET_VALUE` 值操作），唯一差异是 `FORM_p_…` 字段 id 前缀与判定表达式里的页面/实体名：一条写 `kuozhanxinxiDto`（扩展信息），另一条写页面自身实体（如 `htmbzxsc`）。**「XXX 填写内容未生成到模板」常就是这个**：用户在 A 页面填 → 落到 A 实体表，而模板占位符指向 B 实体表 → 空，且不报错。所以那份「修一份必须同步另一份」要改成：**先判定模板取数实体是哪一个，再决定改模板外层实体名、还是让另一条链也往该实体写**；盲目同步两份微流程不解决问题。取值目标的反查方法见 `references/contract-template-evidence.md` §6。
- **两个字段的取值互相颠倒时，先分清「换摆放 / 换绑定 / 改表达式」——别用一句「不行」打发。** 微流程 `FORM_p_<数据项>_p_<表单组件id>_p_<控件实例id>` 解析的是三个硬 ID：**拖动控件在页面上的位置不改变任何 ID**，对取值无用；**交换两个控件的数据项绑定**机制上成立（引用按控件实例 id 取值，id 背后的字段换了，取到的值就换过来）；**改微流程里的字段路径**影响最小。三者都是写操作且各有副作用（换绑定会把落库值与其字段语义反转，并牵动其它成对搬运该字段的微流程），选型前必须先跑一遍「除了已知那两条，还有谁引用这两个字段」。判定表、引用格式实锤与影响面反查见 `references/contract-template-evidence.md` §6.5。先把用户提的改法用机制术语复述（改的是哪个 ID）再判可行性——把「交换绑定」当成「拖动位置」回答，是答错了另一个问题。
- **微流程定义在 `udc_microflow_info.data_schema`，不在 `json_schema`**（后者常为 `NULL`）。`data_schema` 是个 70KB+ 的 JSON，顶层 `{endNode, output, input, sourceType, trigger, nodes}`；`sourceType=PAGE` + `trigger.type=MANUAL` = 页面手动触发。逐节点打印 `actionType` / `caption` / 条件 `description` / `targetName`，别整体 grep 关键词了事——同一个 `SET_VALUE` 值操作在两份微流程里长得一模一样，只有字段 id 前缀能区分落点。
- **合并拆散占位符后必须重新输出 `${}` 包裹**——正则把 `$`/`{`/`}` run 消费掉后只拼名字文本，占位符会变裸字段名，渲染彻底失效。
- **替换句前检查相邻 run 已带的标点**：括号/重复从句的后半句常独立成 run 且自带「，」，新文本再补逗号就成双逗号。
- **拆散形态多样，固定三段式正则会漏**：名字可再拆 2-3 段、`}` 带尾随空格、`}` 混在名字 run、两占位符连写共享 `}${`。用 `<w:t>` 文本级状态机 + 多遍收敛（见 references）。
- **python f-string 输出 `${}` 写作 `${{{name}}}`**；单个 `}` 在 f-string 里直接 SyntaxError。
- **只改占位符里的那个字，别全文替换同义字。** 一字节修法（占位符 `其它` → caption 的 `其他`）必须锚在完整 run 上：`doc.replace('<w:t>品质服务其它补充</w:t>', '<w:t>品质服务其他补充</w:t>')`，替换前先断言**命中数 == 1** 再动手。同一份模板的正文里也常有 `其它补充：` 这类普通文字（它是对的、不能动），用 `doc.replace('其它','其他')` 会连带改坏正文。改完两条断言一起跑：占位符侧新写法 +1、旧写法归零，正文侧同义字出现次数与源一致。
- **一字节替换的校验用「标签计数与源一致」而不是「占位符计数不变」。** 同名占位符在多份实体上并存时计数会因口径变化而误导；`<w:p>` / `<w:r>` / `<w:t>` 三对开闭计数与源文件逐项相等、XML 只增减目标那几字节，才是这次改动没伤到结构的硬证据。
- **枚举超长选项（>100 字）选中后整段塞进正文行会撑爆排版**——让该占位符在模板里独占段落，或精简选项文本。
- **`ctp_enum_item.name` 是 JSON**（`{"zh_CN": "..."}`，部分行是纯文本）：展示/比对前先 try-parse，别拿原始 JSON 串当选项名。
- **核查「这个 bug 改没改」**：低代码侧微流程/页面**没有历史版本表**，只能拿 `udc_microflow_info.update_time` / `udc_page_schema.update_time` 与 bug 提出时间对比（晚于 = 有动作，再看内容是否相关）；Java 侧用 `git log --since=<bug提出日> --grep=<关键词> --all`。不要凭「感觉改过」下结论，每条需求点单独给证据。
- **SQL LIKE 里 `_` 是单字符通配符**：`LIKE '%c_e_s%'` 会误命中 `process`/`access` 等词，命中数虚高。精确匹配列名/字符串用 `LIKE '%c\_e\_s%' ESCAPE '\\'`，或拉回 Python 后精确子串判断。命中后必须抽查上下文确认是真字段引用还是噪声。
