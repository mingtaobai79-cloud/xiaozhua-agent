### 失效的根因不是篡改，是**脱敏**（已定位到具体提交）

`git log` 显示这三处全部由 `2e0d1d8d`（2026-10-20「沉淀归位机制 + 客户信息脱敏」）改动，
改动性质是**机械替换客户标识**，逐条可验：

```text
flow-node-tree.md   L53  函数节点树路径末段：<客户应用名 25 字符> → <代号 24 字符>
engine-behavior.md  L27  gateway_base：<客户域名> → <example.com 形态>
engine-behavior.md  L27  default_app_id：<客户应用名> → <代号>
engine-behavior.md  L77  redirectUrl 主机：<客户 SSO 域名> → <描述性写法>
engine-behavior-live-*.json  12 行同步替换
```

（此处不写原值：本目录 README 是结论区，按 `tests/test_deidentification.py` 不得出现客户标识。）

**字节差**：客户应用名 token（25 B）→ 代号（24 B）= **-5 B**，
与格1 实测差 **完全吻合**。格3 三处替换合计 **-11 B**，也与实测吻合。

⇒ **这不是文件被改坏，是"冻结哈希"与"必须脱敏"两条规则撞上了。**

### 正确的判断（写在这里，避免下一个人重算一遍）

1. **格1/格3 的内容 PASS 结论仍然成立**：改的只是应用名 token / 域名 / appId 的字面值，
   `STATUS.md` 记录的判据（端点、必填、五态响应形态、计数）全部未变。**变的是"被观测对象的代号"。**
2. **但"任何写入使 PASS 失效"这句字面声明现在为假**。不能一边说冻结一边让人以为哈希还对。
3. **不能再"重算哈希把 STATUS 改绿"**：那等于用后来者的手把冻结证据改成新值，
   抹掉"这里发生过脱敏"这一事实。**正确做法是保留旧哈希 + 标注失效原因与时点。**
4. **原始客户标识在仓库里确实不该出现**（用户 2026-10-20 明令，`tests/test_deidentification.py` 守着）。
   所以不能"还原原文来对齐哈希"。

**⇒ 结论：`STATUS.md` 里这 2 处（+1 处证据件）应改为「历史时点绑定值 + 【当前 2026-11-07】
因脱敏失效，内容等价性说明」，而不是改数字。本目录 README 就是这条判断的落点；
`STATUS.md` 本身**未改**（改动需用户裁决，见进度记录「待裁决」）。**
