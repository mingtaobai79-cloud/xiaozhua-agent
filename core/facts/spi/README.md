## 二、★ 三份文件都写着同一条判据边界（本目录最贵的一句话）

`spi-ext-runtime.md` §1 与 `spi-ext-live.md` §1 原文：

> **配置启用 ≠ 插件已加载 ≠ 实现被调用**
> **通道不可达 ≠ 运行态未发生**（不可达是探测面问题，非被测系统事实）

这句话在三份文件里反复出现，因为它是这一域**最容易误判的地方**：
- 看到 Nacos 开关 = true → 只能说"配置启用"，不能推"插件已加载"
- 探测通道 0 响应 → 只能说"探测面不通"，不能推"系统没这功能"

**并且 `spi-ext-runtime.md` 明文禁止重复取证**：
> 本格禁重复/改动其配置面主张（**同格两审 = 禁循环**）

⇒ 修改任何一份前先读它头部的「关联冻结格」声明，别在另一格里重复同一主张。

### ★ `evidence/live/` 的 e1–e9 是一份「通路攻防记录」，不是九次成功取证

`evidence/live/` 的 9 件按编号顺序记录了**同一条观测通路的失败与修复过程**：

```text
e7  同边界复测 → BLOCKED
e8  本线补充复测 → 批0 本地预检命中锚，批1 实连 Host key verification failed（ssh rc=255）
    → 0 pod / 0 字节 / 0 sha256，明确记「本批不构成新的 LIVE 证据」
e9  改用纯 ASCII 本地路径 + 已核验锚 → 三批均 rc=0，拿到直读值
```

**判据（e8 原文）**：`host-key 绕行 0`、`重试 0`、`写面 0`——失败时**不绕行、不改 known_hosts、
不 ssh-keyscan**，只如实登记 rc 和"未取得"。这是本仓库把「失败」也当证据的样板。

**读这 9 件的正确姿势**：想看"运行态到底证明了什么"，读 **e9**；
想看"哪些通道试过不行、为什么不绕过去"，读 **e7/e8**。**不要跳过 e8 只读 e9**——
e8 记录的是"不绕行"的纪律，那是 e9 之所以可信的前提。

⚠️ `evidence/live/` 各件含**客开模块标识与客户环境信息**，已被 `tests/test_deidentification.py`
与相关规则覆盖；**本 README 一律不写模块名 / jar 名 / 客户域名**，只写事实形态。
