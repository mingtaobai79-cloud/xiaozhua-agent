# 微流程验收套件（抽自仓库根 `验收/`，2026-11-07）

## 这是什么

仓库根曾有一个未纳入 git 的 `验收/` 目录：**20 个业务场景 × 2 变体 = 41 份完整 dataSchema**，
每份都是可直接提交给平台的真流程结构（22–28 节点），另有 `INDEX.md`（业务 ↔ 节点类型对照）
与 `COVERAGE.md`（节点类型使用频次统计）。

## 为什么只抽两个索引进来

`验收/*.schema.json` 是**某个客户应用（应用 ID 已脱敏为保留段）的实例数据**：
- 内含 `com.seeyon.<tenant>xxxx.dto.YsFull6956Dto` 等客户业务 DTO 全限定名
- 每份 3 万–10 万字节，41 份合计约 2 MB
- 零程序读取（`rg` 全仓确认无代码/测试引用该目录）

真正有复用价值的是**结构知识**，不是这 41 份实例：

| 抽进来的 | 价值 |
|---|---|
| `INDEX.md` | 20 个采购/供应链业务的**节点编排方案**：每个场景用哪些节点类型、几个节点、几个真实取值、几个校验 —— 这是"业务 → 微流程结构"的映射样本 |
| `COVERAGE.md` | 18 种 actionType 在 41 份流程里的**使用频次**（CREATE_VARIABLE 134 / BRANCH 120 / …），可判断哪些节点是高频必备、哪些是场景专用 |

实例 JSON 留在仓库根 `验收/`（未跟踪、未被忽略、不参与测试），未删除。

## 怎么用

- 要生成某个采购业务场景的微流程时，先查 `INDEX.md` 找同类场景的节点组合，再看 `COVERAGE.md`
  判断该组合是否属于高频模式。
- 需要真实 schema 样板时，从仓库根 `验收/<场景>-v1.schema.json` 取，
  **取用前先把客户 DTO 全限定名替换为保留段**（`com.seeyon.9000000000000000001.dto.*`）。

## 边界（不要高估）

- 这些 schema 是**某一次构建的产物**，没有版本戳、没有平台回读确认。
- `INDEX.md` 的"校验 0 / 闸门 0"表示当时没跑校验和闸门，**不是**表示结构正确。
- 不代表 18 种节点已被运行时验证；节点能力等级仍以
  `core/facts/udc/microflow/capability-matrix.md` 为准。
