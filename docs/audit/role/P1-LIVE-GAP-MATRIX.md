## 3. 六个写端点的风险排序（决定补证优先级）

排序依据：**误调用后的破坏面 × 可恢复性**，而不是「接口重要程度」。

| 端点 | 破坏面 | 可恢复 | 优先级 | 理由 |
|---|---|---|---|---|
| `delete-resource/app/{appId}` | **单应用全部角色授权**（rr_app 全清） | 需完整备份 + 重放 | **P0 不补，只防护** | 破坏面最大、且**一次调用即批量**。补证成本 >> 收益，应改为「登记为禁用面」 |
| `delete-resource/{id}` | 单角色授权行 | 可重建（`func-auth` 覆盖式写） | **P1 不补** | 与 #13 `func-auth` 是同一张表的删/写两向，`func-auth` 已 LIVE 闭合其表语义 ⇒ 边际信息低 |
| `create-system-admin` | 授予系统管理员身份 | 可删角色？未验 | **P1 值得补** | 涉及**权限提升**，且「有则不创建」是幂等语义，需实测确认 |
| `func-auth-all` | 批量写多角色授权 | 覆盖式，可重放恢复 | **P2 补** | 与 #13 同语义，仅入参变 List；但**批量**意味着单次影响面放大 |
| `update` | 角色元数据（name/code/description） | 可直接改回 | **P3 补** | 影响最小 |
| `create` / `delete`（角色本体） | 建/删角色 | delete 后重建 id 会变 | **P3 补** | 需在测试应用内建临时角色，注意「禁第 2 个」类红线 |

> **一句话**：**#4 / #5 我建议直接判「不补 LIVE」**，改为在契约里登记为「禁止调用面 + 调用前必须整表备份」。
> 理由是它们的信息增量已经由 #13 `func-auth` 覆盖（同表覆盖式语义已实证），再跑只是增加破坏风险。

#### 4.4.1 `role-auth-all` 这条为什么必须留在清单里（不能当已闭合）

它的入参语义有一个**反直觉的坑**，任何后续补证者都会踩：

```
code 参数 = 资源 code（不是 appId）
不传 code   → 走 selectByAppId 全量分支，但 admin=false 过滤后匹配集为空
              ⇒ 返回 11 角色 + resourceList 全空   ← 看起来像"这个应用没授权"，实际是过滤掉了
传真实 code → code=2084600749018399891 → 11 角色 / 289 行
              code=9183843213439484192 →  21 行
```

**教训**：这个端点「不传参返回空」**不等于**「没有授权数据」。
若把空 resourceList 当作出结论（"该应用无授权"），就是**假阴性**。
P3 已经踩过一次并撤回，**必须在契约里写死，避免下一轮再踩**。

#### 4.4.2 ⚠️ 一处入口判断的订正（2026-10-18 12:10，auditor 复核 + 我回查）

> **原文（本文件早期版本，以及 `P1-STRUCTURE-SUPPLEMENT.md` §3.2/§3.3）曾判 #12「页面无入口、只能手调」。
> 这个判断是错的。**

硬证据（bundle 原文）：
```
组件 U（功能权限总表）的 useEffect：
  (0,n.useEffect)(()=>{ l((0,N.ig)(u.vL)) }, [l])          ← 进页面即自动调用
  N.ig → thunk "function-permission/fetchAllRoleAuth" → op 层 ig → udcCtpUserRoleRoleAuthAllPost   (#12)
另一入口：thunk "function-permission/fetchRoleAuthByCode"  → op 层 ig  → 同样是 #12
```
完整链路见 `P1-FUNCAUTH-BRANCH-TRACE.md` §1.2。

**订正后的正确表述**：

| 项 | 旧（错） | 新（对） |
|---|---|---|
| #12 有无 UI 入口 | 无 | **有，自动触发（读操作）** |
| 为什么只能手调才发现 409 | 「页面不可达」 | **参数语义坑（`code` 是资源 code 非 appId）**，与可达性无关 |
| 该不该补 LIVE | （原判据：没入口所以补不了） | **不补，但理由不同**：有入口 + 已有 P3 LIVE 佐证 + 无独立信息增量 |

> **auditor §四 也主动撤回了同一条旁证**，双方口径现已一致。
> **成因**：这句「bundle 无调用点」写在 P1-FUNCAUTH 追溯**之前**；
> 追溯完成后我只在补充文件 §3.4 加了更正块，**没回改 §3.2/§3.3 的旧结论** ——
> 这是「**新证据不回改旧结论**」的典型脱节，比单纯数字错严重，已单列为教训。

> 这两项都**只需翻已有证据文件核对，不需要新调用** —— 已完成（本 §4.4）。
> 结论：#11 零成本升级为 LIVE；#12 保留为「LIVE 但入参语义特殊，需专门标注」。

## 5. 与设置域体例的差异（P1 这份缺什么）

对照 `SETTINGS-TABS-CALLCHAIN.md`，角色域 P1 目前**缺少三块标准结构**：

| SETTINGS-TABS 有 | 角色域 P1 现状 | 影响 |
|---|---|---|
| §0 版本边界表（后端镜像/前端壳/远端入口/静态存储 4 项） | P1 只有 jar 路径，无镜像 tag、无前端 bundle 版本 | 无法判断「本地反编译产物 = 部署代码」是否仍成立 |
| 每种调用形态的**真实 chunk 名 + 哈希** | P1 有 `web/*` 但未按形态归类 | 复现者无法定位 chunk |
| 端点 → **页面元素**的对应（哪个按钮触发哪个端点） | P1 只有端点表，无 UI 映射 | 补 LIVE 时不知道该点哪里 |

**⇒ 若要收口 P1，建议先补这三块，再谈 LIVE 缺口。**
否则补到一个 LIVE，也只是「又多一条零散证据」，不构成可复用的契约。
