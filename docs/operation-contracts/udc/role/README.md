## 二、`15 个端点`是**可复算**的，不是记下来的

文档原话（§全局等级总表），并且我实测跑过：

```
cd docs/audit/artifacts/udc-user-5.3.517-contracts
F=UdcRoleController.javap.txt
grep -cE 'annotation\.(Post|Get)Mapping\(' "$F"    # → 15（方法级）
grep -cE 'annotation\.RequestMapping\('     "$F"    # → 1 （类级，别混入）
grep -oE 'value=\["[^"]*"\]' "$F" | wc -l          # → 16
```

**实测结果：15 / 1 / 16 —— 与文档完全一致。**
16 = **1 个类级基路径（`udc/ctp-user/role`）+ 15 个方法级路径**，且每个方法路径各出现 1 次。

⇒ 这就是"双向完备性"：不只数总数对，还证明**每个方法路径只出现一次**（无重复、无遗漏）。
⇒ 判据：**"我数了 15 个"和"我能证明恰好 15 个且无重复"是两件事**，后者才叫完备。

### ⚠️ 复算有一个必须知道的前置

> **必须用 JDK 21 的 javap 产物**。用 JDK 8 的 javap 重新生成，
> `annotation.(Post|Get)Mapping(` 会得 **0**（JDK 8 不展开注解类名）。

⇒ 谁用 JDK 8 复算会得出"0 个端点"，然后判定这份契约是编的。
⇒ **这是复算说明里最容易被略过、也最容易让人误判的一句。**

## 三、两条 DANGER-ZONE 与一条"必然触发"

### ① `func-auth` 是**覆盖式**，不是追加

```
若该角色原有 N 条授权，调一次传 1 条 → 结果 N → 1（不是 N+1）
```

响应里的 `content:N` 是**写入后的总条数**，不是本次增量。
⇒ **用它试写会毁掉该角色的既有授权。** 生产上必须先 `role-auth`(#11) 读出全量 → 改 → 整包写回。

**这里同时演示了怎么分清证据等级：**

| 结论 | 等级 | 依据 |
|---|---|---|
| "覆盖式 / 全删全建"这个**机制** | **LIVE 实测** | S5 §2 四次写，`content:1/1/1/2`，物理 id 全换 + delta 提交把存量抹除 |
| "**47 → 1**"这个**数字** | **推算，不是实测** | 47 是 `ContractAdmin` 的现有授权数；"47→1"是**假设句**（"若提交 delta"）的算术推演。**本轮从未对 47 条的角色做过实测** |

本域四次实测的载体是基线 **1 条**的角色，所以实测序列是 `1→1 / 1→1 / 1→1 / 1→2`。

⇒ **判据：机制可以是 LIVE 的，而解释机制的那个数字是推算的。两者必须分栏写。**

### ② `role-auth-all` 的返回范围**不可泛化**

`code` 参数是**资源 code**，不是 appId、也不是角色 id。不同样本观察到不同返回行为：

| 情境 | 入参 | 结果 | 证据边界 |
|---|---|---|---|
| P3 历史样本 | `{appId}` | 11 角色，`resourceList` 空 | 仅适用当时应用/数据/身份 |
| P3 历史样本 | `{appId, code:"…391"}` | 11 角色 / 289 行 | 不可推断所有 code/应用 |
| P3 历史样本 | `{appId, code:"…192"}` | 11 角色 / 21 行 | 资源子树过滤 |
| test2 `9000000000000000002`（2026-10-19） | `{appId}`，无 code | 11 角色，共 413 项 | 只证明该次调用上下文 |

> **操作规则**：读取实际 response、明确当前 app/身份和数据上下文，再选择判据；
> 省略 `code` 时**绝不能仅凭空数组判"无授权"**，也**不能假定得到完整授权总览**。

**并且它撤回了一个自己此前的结论：**

> P3 原"**409 条与 DB 互证**"结论**已撤回**：参数/聚合口径不成立；
> 跨角色 `resourceList` 求和不是全局权限总数。

⇒ **这是本仓库唯一一处明确写"已撤回"的地方。** 撤回比新增更值钱——
它挡住了后来者继续用一个错的数。

### ③ 进「角色权限」页会自动触发 `create-system-admin`（#15）

> ⚠️ 进入「角色权限」页会**自动触发** `create-system-admin`（#15），**这是必然行为**。

⇒ 探针只要打开这个页面就在写。**「只读观测」在这个页面上不存在。**
⇒ 这解释了为什么角色域的风险登记（`#11 DANGER-ZONE`）特别厚。

### ④ 权限面板 31/31 复选框 disabled 不是「只读」，是「查看模式」

⇒ 看 UI 状态推断权限语义会错。`disabled` 表示当前身份是查看模式，不代表不可写。
